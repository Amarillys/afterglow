# 性能排查：开久了声音卡顿（2026-10-29，v0.5.1 → v0.5.2）

用户反馈："开久了声音好像会卡顿"，要求查有没有内存泄露。

## 结论
- **没有内存或音频节点泄露。** 7 分钟高压运行后强制 GC，存活节点回到约 190 个（和刚进入时差不多），JS 堆约 2 MB，DOM 节点和监听器数量稳定。
- **卡顿更可能来自音频线程负载。** 密集节奏主题加上频繁交互时，v0.5.1 的渲染负载是 45–61%。换成更慢的 CPU、开着其他标签页或用真实声卡，可能超过 100%，那时就会卡顿或爆音。负载主要来自铃：铃是最常响的声部（密集主题约 8 个/秒），每个铃有 6 个振荡器。
- **v0.5.2 在同样负载下把渲染负载降到约 26%**（A/B 对比 47.5% → 25.9%），听感不变。

无头 Edge 用的是假音频设备，绝对数值只适合用来对比。同一个用例两次测量常差 ±3 个百分点，所以每个对比都跑多轮、交替顺序。

## 测量（cost-check：所有一次性声部从进入前就静音，每个用例换新页面）

| 用例 | 渲染负载 |
|---|---|
| 固定图（潮声 + 混响 + 回声 + 两个压缩器） | 13–14% |
| 只关潮声 | 11–13% |
| 只切掉卷积器输出 | **2%** |
| 只切掉回声环输出 | 11–15%（几乎不变） |
| 绕过输出限幅器 | 13–14%（几乎不变） |
| 空 AudioContext | 0.1% |
| v0.5.1：+15 铃/秒 | 38–49% |
| v0.5.1：+15 水滴/秒、+15 碎片/秒 | 25–32%、36–37% |
| 15 铃/秒停止 8 秒后 | 回到固定图水平 |

- 固定图的成本几乎全在卷积混响上（约 12 个百分点）。卷积器的输入是静音时也照常计算，所以只断开输入测不出它的成本，必须断开输出。上一版文档里"切掉混响省 8 个百分点"的数字就是这样测偏的（而且当时静音前已经排好的 pad 还在响）。回声、潮声和压缩器都很便宜。
- 已经停止的声部不花渲染时间，浏览器会自己回收。所以"声部结束后主动 disconnect"没有收益，没做。
- 卷积器成本随冲激长度分级增长（verb-cost.mjs）：6.5 s ≈ 13%，5.75 s ≈ 13%，5 s ≈ 12%，4 s ≈ 8%，3 s ≈ 7%，1 s ≈ 4%。
- 拆开一个铃（voice-cost.mjs，15 铃/秒，比空闲多出的部分）：6 个振荡器加包络是大头，低通、声像和三路发送加起来差不多同样多。换成预渲染缓冲区并把低通也算进缓冲区以后，增量从 22.5 降到 6.2 个百分点。

## 做了的优化
1. **铃改成预渲染缓冲区**（`js/audio/voices.js` 的 `bellBuffer`）。每个（音高, 长度）在 JS 里算一次：同样的泛音、同样的包络（线性起音 + setTargetAtTime 的指数衰减）、同样的停止时间，再按 Web Audio 规范的公式过一遍同样的低通（Q = 1 dB）。播放时只用一个 AudioBufferSource 接进原来的 strip，力度和响度修正放在 strip 的输入增益上。
   - 和旧铃逐采样对比（bell-compare.mjs，离线渲染）：误差能量比信号低 78–112 dB，听不出来。
   - 每个缓冲区在主线程烘焙 2–5 ms。音符提前 4.4 s 调度，所以不影响声音。LRU 缓存 32 个，最坏约 20 MB。密集主题下每秒新建缓冲区 0.2–2 个。
   - 文档里原来计划的"每个泛音按自己的衰减停止"，旧代码其实已经这样做了（`partial()` 各自 `stop`）。新缓冲区保留了同样的停止点。
2. **混响冲激按绝对时间衰减，在 -60 dB 处结束**：形状仍是 `(1 - t/6.5)^3.2`，RT60 不变，长度从 6.5 s 变为 5.75 s。去掉的尾巴比混响总能量低约 69 dB。省得不多（不到 1 个百分点），但没有代价。没有缩到 5 s：那样会在 -41 dB 处截断，安静时能听出尾巴变短。
3. **水滴主体 1.6 s 停止**（原来 2.2 s）：那时包络已在 -43 dB，和铃的泛音停止点一致。

## 没做的
- **复音上限**：新铃很便宜，15 铃/秒只比空闲多约 8 个百分点；限制同时发声的铃反而可能在密集段听出来。
- **碎片 chime 预渲染**：每次都随机微调泛音，缓存会让"每次都有点不一样"的听感消失；碰碎片的频率也低（不到 1 个/秒）。
- **去掉一个压缩器**：两个压缩器合计不到 1 个百分点。
- **混响再缩短**：见上，会改变空间感。

## A/B 与长时间验证
`ab-check.mjs`（上一次提交 vs 工作区，交替 3 轮，2 倍速密集主题 + 每 0.5 秒随机交互，每次采样 20 秒）：

| | 画面绘制中 | 页面隐藏 |
|---|---|---|
| v0.5.1 | 47.8% [61.8, 41.6, 39.9] | 47.5% [45.0, 45.3, 52.1] |
| v0.5.2 | 27.3% [32.6, 24.2, 25.0] | 25.9% [27.2, 25.8, 24.7] |

`leak-check.mjs 420`：全程渲染负载 15–31%（v0.5.1 的 200 秒试跑是 30–61%），存活节点 540–1120（原来 1100–2100）。结束并 GC 后剩 188 个节点、2.1 MB 堆，没有哪类节点比中途 GC 时多 20 个以上。

修好的一个测试问题：上次选择的主题会在进入时自动恢复，所以 leak-check 的"世界节奏"阶段其实一直在放主题。现在进入后先 `stop()`。上面 420 秒那次还是旧行为，两个阶段都是主题。

## 还需要用户提供
真实环境的信息：浏览器（Chrome / Edge）、卡顿时是世界节奏还是节奏主题（哪一档、几倍速）、开了多久开始卡、卡了以后会不会自己恢复、是否同时开着很多标签页。可以在 DevTools → More tools → WebAudio 里看 Render Capacity。

## 工具
- `test-scripts/cost-check.mjs [轮数] [用例过滤]`：固定图各部分、各声部爆发的渲染负载。另有进程树 CPU，噪声大，仅作参考。
- `test-scripts/voice-cost.mjs [轮数]`：拆开一个铃看各部分的成本（`oscbell` 是 v0.5.1 的铃）。
- `test-scripts/verb-cost.mjs [轮数]`：卷积器成本和冲激长度的关系。
- `test-scripts/bell-compare.mjs`：预渲染铃和振荡器铃的逐采样对比、烘焙耗时。
- `test-scripts/ab-check.mjs [轮数] [曲子] [提交]`：某次提交（git archive 到 `test-scripts/.ab/`）和工作区交替对比。
- `test-scripts/leak-check.mjs [秒] [曲子]`：长时间泄露和负载检查；每行带各声部每秒调用次数和新建缓冲区数。
- `test-scripts/tree-cpu.ps1 <pid>`：进程树的 CPU 秒数。`cdp.mjs` 的 `launch()` 返回值新增 `pid`。
- 原始输出存放在 `test-results/`（已 gitignore）。
