# 性能排查：开久了声音卡顿（进行中，2026-10-29）

用户反馈："开久了声音好像会卡顿"，要求查有没有内存泄露。基于 v0.5.1。

## 已有结论

### 1. 没有发现内存或音频节点泄露
工具：`node test-scripts/leak-check.mjs [秒数] [曲子]`。它通过 CDP 的 WebAudio 域统计实时 AudioContext 里节点的创建和销毁，同时记录 JS 堆、DOM 节点、事件监听器的数量。压力远大于正常使用：每 0.5 秒随机响一个音，偶尔拖动、扫弦；一天只有 2 分钟；后半段切到 nerine 的 2 倍速、密集档节奏主题。

200 秒的试跑结果：

| 时刻 | 阶段 | 存活节点 | 累计创建 | 渲染负载 | JS 堆 | 监听器 |
|---|---|---|---|---|---|---|
| 5s | 开始 | 89 | 89 | 16% | 1.9 MB | 29 |
| 25–101s | 世界节奏 + 连续点击 | 300–410（首个采样 1369 后回落） | 5330 | 21–38% | 1.5–2.5 MB | 27 |
| 103s | 强制 GC 后 | 301 | 5422 | 25% | 1.7 MB | 27 |
| 125–182s | 主题 2×、密集 | 1300–1870 | 21305 | **54–61%** | 2–3 MB | 27 |
| 200s | 停止后强制 GC | 198 | 21617 | 20% | 2.3 MB | 27 |

- 停下来、做过 GC 以后，存活节点回到约 200 个，和开始时差不多。和中途 GC 时相比，没有哪类节点多出 20 个以上。
- JS 堆一直在 2 MB 左右，DOM 节点和监听器数量稳定，结论是没有泄露。
- 浏览器会正常回收已经停止的音频节点。

### 2. 卡顿更可能是音频线程负载太高
- 密集主题加上频繁交互时，渲染负载到 55–61%，同时存活约 1500 个节点。换成更慢的 CPU、开着其他标签页，或者用真实声卡，很可能超过 100%，那时就会卡顿或爆音。
- 固定图本身就不便宜（`test-scripts/cost-check.mjs`，所有声部静音后测）：
  - 固定图（潮声 + 混响 + 回声 + 两个压缩器）：29.4%
  - 切掉混响后：21.5%，说明 6.5 秒的卷积混响约占 8 个百分点。
  - 回声、潮声、压缩器、空 AudioContext 分别占多少，以及 5 个铃/秒、15 个铃/秒的增量，都**还没测出来**。上一版脚本 reload 之后读成了旧 context，结果是 NaN；已经改成取最新的 context，需要重跑。
- 注意：无头 Edge 用的是假音频设备，绝对数值只适合用来对比，不能代表真实机器。

## 下一步

1. 重跑 `node test-scripts/cost-check.mjs`，补齐各部分的成本。
2. 按测量结果挑优化项，每改一项都用 cost-check / leak-check 对比前后，不要凭感觉改：
   - 每个泛音按自己的衰减时间停止，不要所有泛音都等到最长的尾音（bell / chime 的 `partial()` 在 `js/audio/voices.js`）。预计 bell 的振荡器存活时间能减少约 37%。
   - drop 主体的 `osc.stop(t + 2.2)` 可以提前到约 1.6 秒（包络 τ=0.32，1.6 秒时已经低于 -40 dB）。
   - 声部结束后主动 `disconnect()` 它的 strip 输出（dry / wet / echo），不要等 GC。需要验证这样是否真的降低渲染负载。
   - 混响冲激响应从 6.5 秒缩短到约 5 秒。冲激的衰减是 `(1-t)^3.2`，与长度相关，缩短时要改成按绝对时间衰减，才能保持原来的 RT60，否则空间感会变。
   - 密集档或高 BPM 时限制同时发声的铃的数量（复音上限）。
   - 两个 DynamicsCompressor 串联（总线压缩 + 输出限幅），看看成本是否值得。
3. 改完后跑一次 7 分钟的 `leak-check.mjs 420`，确认负载下降、仍然没有泄露。再跑 smoke.mjs / smoke-ref.mjs / fps-check.mjs 回归测试。
4. 请用户提供真实环境的信息：浏览器（Chrome / Edge）、卡顿时在用世界节奏还是节奏主题（哪一档）、开了多久开始卡、卡了以后会不会自己恢复、是否同时开着很多标签页。可以让用户打开 DevTools → More tools → WebAudio，看 Render Capacity。
